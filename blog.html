Day 41 — WAF Raft Cluster Wiring Complete

Big milestone today. Wired the Go Raft cluster into the Sentinel control plane. This means the control plane can now run in HA mode — multiple controllerd instances, leader election, log replication, the whole thing. The implementation is straightforward compared to most Raft setups I've seen. Single-file Raft in Rust for the data plane cluster, and a separate Go Raft for the control plane. All write endpoints (site creation, rule mutations, alert management) now route through `cluster.Propose()`. If you hit a follower, it returns a 503 with an `X-Sentinel-Leader` header so your client can redirect. Tested with a 3-node cluster. Election works. Persistence works. The single-node shortcut (empty peers → immediate leader) means you can still run it standalone without changing any config. 5 tests all pass. Env-driven config: `SENTINEL_RAFT_ADDR`, `SENTINEL_NODE_ID`, `SENTINEL_RAFT_PEERS`. This was the last piece of Phase 5 wiring. The WAF now has full HA capability end to end.

Day 40 — Raft Deep Dive, Cluster Design Decisions

Spent the day designing the Raft implementation for Sentinel. The data plane already has a Rust Raft (single-file, TCP JSON RPCs, atomic persistence). Today was about the control plane side — Go Raft for the admin API cluster. The tricky part is the dual-plane architecture. Rust data plane nodes are completely stateless — they can scale horizontally behind any L4 LB. But the Go control plane needs consensus because it owns the source of truth (site configs, rules, RBAC, audit). If two admins make conflicting changes, someone has to win. Decision: separate Raft clusters. Data plane uses its own lightweight Raft for config version propagation. Control plane uses Go Raft for API-level consensus. They don't talk directly — the data plane polls the control plane's internal config endpoint every 5 seconds. This keeps the data plane simple and the control plane authoritative.

Day 35 — Retrospective: What 40 Days of Building Security Tools Taught Me

Took a step back today. When I started at ESDS in June 2025, I had never built a vulnerability scanner. I'd used Burp Suite and ZAP. I'd run SQLMap. I understood OWASP Top 10 academically. But building a scanner from scratch? That's a completely different problem. The thing nobody tells you about DAST scanners: the scanning engine is the easy part. Sending a SQLi payload is maybe 100 lines of Python. The hard parts are everything around it — the crawler that needs to handle SPAs with hash routing, the deduplicator that needs to not silently drop findings, the false positive filter that needs to distinguish a real SSTI from CSS color codes, the multi-tenant isolation. On the WAF side: performance isn't about writing fast code. It's about architecture decisions that compound — Aho-Corasick in a single pass, early-exit at 505ns, fusing proxy+WAF, Rust's zero-GC. Together they add up to 5-125× faster than every competitor. The biggest lesson: ship features that work end-to-end. The config sync between control plane and data plane took a full day. It's not flashy. But without it, adding a site from the dashboard does nothing. That's the difference between a demo and a product.

03 Jun 2026

Day 34 — Killing 95% of False Positives in One Session

Ran a full scan on esds.co.in today. The results were terrifying — 154 CRITICAL, 382 HIGH. For about 30 seconds I thought I'd discovered a catastrophe. Then I actually looked at the findings. Nearly every "critical" was a debug endpoint detection firing on SPA catch-all routes. Modern SPAs return HTTP 200 with the app shell for every URL — including `/actuator/env`, `/phpinfo.php`. The API gateway scanner was checking for these paths, getting 200 OK, and reporting them as exposed debug endpoints. 64 false positives from one bug. The SSTI scanner was even more embarrassing. It sends `{{7*7}}` and checks if `49` appears in the response. That works fine — until the response body contains CSS with `rgba(249, 249, 249, ...)`. The number 49 appeared in a color value and the scanner flagged it as CRITICAL SSTI. Fixed both with content-aware filtering — canary probe + content hash comparison for SPA catch-all, strip <style> blocks + word-boundary regex for SSTI. Also found four crawler bottlenecks: cached domain lookup (~15-20% speedup), parallel JS bundle mining (~40-60% of JS phase), broader link extraction, deferred redirects. Net result: scan time cut ~40-50%, false positive rate dropped from 74% to under 15% for criticals.

Days 32–33 — Weekend Sprint: eBPF Pre-Filter Deep Dive

Weekend work. When you're building something you care about, the distinction between weekday and weekend blurs. Spent Saturday and Sunday deep in eBPF/XDP territory. The eBPF pre-filter was working but entirely in software mode. The kernel XDP path existed behind `--features kernel` but was never wired into the proxy's hot path. Wired it today — `EbpfManager.is_blocked(ip)` checks both the exact IP hash set and the CIDR block list. If blocked, the proxy drops the connection before TLS handshake. The kernel XDP path goes even further — drops the packet at the NIC driver level. Measured the impact: software path adds about 200ns per lookup. Kernel XDP is essentially free — the NIC drops the packet in hardware if you have a supported card (Mellanox/ConnectX). Added `ebpf_drops()` counter to telemetry — the dashboard now shows a stacked bar chart of kernel vs userspace drops. 30-70% of traffic gets dropped before the WAF data plane even sees it. Enterprise customers care about this because their cloud bill drops by 30% when the WAF stops processing garbage traffic.

22 May 2026

Days 22–23 — Reports That Survive Server Restarts

Two days on data durability. The WebScanner had a fundamental problem: scan findings only lived in memory and filesystem files. If the server restarted, all finding detail was gone. Report regeneration? Impossible. The `findings` Postgres table existed but was never written to by web scans. Wired `save_findings` into the scan completion pipeline. Each finding goes in with core fields (type, severity, URL, confidence) plus JSONB metadata for extras — param, method, payload, AI advice, false positive reason. The tricky part was report regeneration after restart — `_ensure_findings_loaded()` lazy-loads from DB, flattens findings, wraps as SimpleNamespace objects, and regenerates HTML. Same for PDF. Wrote 11 tests for the persistence layer. Full round-trip: save findings → restart → regenerate report → verify content matches. 87 tests total, all green. This feels like boring infrastructure work but it's the difference between a tool that loses data and a tool you can rely on. If a security scanner loses its findings, it's worse than useless — it gives false confidence.

Day 19 — Two Bugs, Zero Findings. The Dedup Disaster.

Today I found two bugs that were silently suppressing most findings from the WebScanner's final report. These bugs had probably been there for weeks. I only caught them because I happened to compare the raw scan output against the report and noticed the numbers didn't match. Bug #1: The `FindingDeduplicator` was keyed on `(vuln_type, param)`. No URL. So all 35 HTTP Verb Tampering findings across 35 different endpoints collapsed to ONE finding in the report. Think about that — 35 endpoints vulnerable, report says "1 finding." Operations team thinks everything's fine. Fix: changed dedup key to `(vuln_type, url, param)`. One line. Weeks of missed vulnerabilities. Bug #2: XHR-captured endpoints treating `?ts=1234` and `?ts=5678` as different endpoints. Same endpoint scanned 30+ times with different cache-busting timestamps. Fixed by normalizing dedup key to path + stable param names, stripping volatile params. Endpoint `get_user_projects_redis` went from 30+ copies to 1. Same day, I overhauled the headless crawler. Four silent bugs fixed: `max_pages=50`→200, `max_depth=2`→4, `#` hash-route links now crawled, `wait_until="networkidle"`→`"load"` for WebSocket apps. And the new crawler clicks things now — hamburger menus, dropdowns, sidebar toggles, tree expanders. Admin panels hide privileged routes behind collapsed menus. Now the scanner finds them.

13 May 2026

Days 13–16 — CRS Rule Engine, Deep in the Weeds

Four days deep in the CRS rule engine. When you're building a WAF, you realize very quickly that the rules are the product. The proxy, the eBPF pre-filter, the dashboard — all of that is infrastructure. The rules are what catch attacks. And getting rules right is hard. The CRS has 25 `.conf` files and 21 `.data` files. Each rule has conditions, transformations, chained rules, paranoia levels, skip-gates, markers. The skip-gate bug was the worst — my compiler was sorting rules by `(phase, rule_id)`, but skip-gate rules have smaller IDs than the detection rules they guard. Switched to source-order compilation. No sorting. Then the false positive on `?id=42`. CRS rule 932236 (Unix command injection) was matching the parameter *name* "id" because the regex had a `^` anchor and "id" happens to be a Unix command. Every request with `?id=VALUE` was blocked. Added rule exclusions. The block/log action parsing bug: CRS rules use `block,log,msg:'...'`. My parser went left to right — `block`→set Block, then `log`→overwrite to Log. Fixed with `primary_action_set` flag. These are the bugs that take 8 hours to find and 5 minutes to fix. You test with SQLi, it blocks. You test with XSS, it blocks. You think everything works. Then a real app gets `?id=42` blocked and you spend hours tracing bytecode.

Day 0 — Why I'm Starting This Blog

I'm a Security Engineer at ESDS Software. I build things — a multi-tenant DAST vulnerability scanner, a next-gen WAF in Rust and Go, exploit tools, detection engines. I spend my days writing code, debugging compilers, fighting false positives, and trying to make security tools that actually work in production. But I have a problem: I don't remember my own process. Six months from now, when someone asks me "why did you choose Aho-Corasick for pattern matching instead of Hyperscan?", I want to have an answer. Not a guess — the actual reasoning I worked through, the benchmarks I ran, the tradeoffs I considered. Right now, that knowledge lives in my head and in scattered SAVE files. So I'm starting this blog. Not to build an audience. Not to become a thought leader. I'm writing this for future me — so I can look back and see where I started, what I was stuck on, and how I actually solved it. I want a place where I can track what I was thinking, what problem I was stuck on, and how I actually figured it out. Most engineers don't document their process. They ship the feature and move on. Six months later they can't remember why they made that design decision. I don't want to be that engineer. Here's where I am right now. The WebScanner has 87 passing tests, 12 DAST modules, a working multi-tenant dashboard, and real findings on real targets. But the findings don't survive server restarts — that's the first thing I need to fix. The Sentinel WAF has 226 Rust tests and 23 Go tests across 10 crates. The data plane works. The control plane works. But they don't talk to each other — adding a site from the dashboard does nothing to the proxy. That's the second thing. This blog covers everything I'm working on: building a production DAST scanner from scratch at ESDS, engineering a next-gen WAF in Rust and Go, fixing bugs that take 12 hours to find and 5 minutes to fix, and all the small decisions that nobody talks about. If you're a security engineer, or you build developer tools, or you just like reading about someone debugging compile errors at 2 AM — this is for you. I'm going to write about both projects as I work on them. The bugs, the late nights, the compile errors that make no sense, the moments where everything finally clicks. This is the raw, unfiltered version of building security tools from scratch. No polished tutorials. No retrospective wisdom. Just what happened today, what I tried, and whether it worked. Let's see where this goes.
